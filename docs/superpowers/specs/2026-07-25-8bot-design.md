# 8bot — Design Spec

Date: 2026-07-25
Status: Approved for implementation planning

## Purpose

`8bot` is a reusable npm package for generating and rendering 8-bit pixelated
2D and 2.5D (isometric) objects — characters, robots, props, and geometric
primitives — for use in webapps, web games, or anywhere else. It ships with a
built-in catalog of ready-made objects and exposes the same primitives used
to build that catalog so consumers can compose their own custom objects
(e.g. a custom "palace" prop) without forking the library.

Inspiration: https://github.com/tkoriginal/pixel

## Non-goals (v1)

- Full 3D/voxel rendering. The core data model must not preclude a future
  `8bot/voxel` module or 3D renderer, but no 3D work happens in v1.
- Hand-authored multi-frame sprite sheets (walk animation is procedural via
  `walkCycle`, not pre-drawn frames — see Movement & Interaction below).
- A physics or DOM collision engine. 8bot exposes bounds/position data; the
  consumer's app decides what "interacting" with a page element means.

## Architecture

Three layers, published as one npm package (`8bot`) with subpath exports so
consumers only pull in what they use.

### 1. Core (`8bot/core`)

Framework-agnostic primitives with no rendering or DOM dependency.

- **Part**: a named pixel grid (2D array of region tags, e.g. `"skin"`,
  `"outfit"`, `"eyes"`, or `null` for transparent) plus an anchor point and
  an optional depth/layer offset used only by the isometric renderer.
- **Palette**: a map of region tag → hex color (e.g.
  `{ skin: "#e0ac69", outfit: "#3355ff" }`). Applying a palette to a part
  never mutates pixel data — recoloring is just picking a different palette.
- **Object definition**: a named set of **slots** (e.g. `head`, `torso`,
  `legs[0..7]`) where each slot accepts one part from a list of valid
  variants, plus a default palette and a list of valid palette overrides
  per region tag. Slots are not fixed to a "head/torso/arms/legs" shape —
  an object can declare any slot names and counts (e.g. an octopod
  declares 8 `leg` slots, a UFO declares none).
- **Composer**: assembles a set of chosen parts + a palette into a single
  **Composed Object** — a flat list of `{ pixels, region, position, layer }`
  ready for a renderer. Same composer output shape serves both flat 2D
  rendering (ignore layer) and isometric 2.5D rendering (layer drives
  projection offset and z-order). No duplicate art is authored for 2.5D —
  it's the same parts, projected differently.
- **Shape primitive**: an alternate, simpler definition used by the
  Primitives catalog (cube/oblongoid/sphere) — a 3D-ish extent
  (width/height/depth in pixel units) plus one base palette color. The
  core auto-derives per-face shading (lighter top, mid front, darker side)
  instead of requiring hand-authored per-pixel grids. Composes into the
  same Composed Object shape as parts, so it renders through the same
  renderers.
- **Registry**: `registerObject(name, definition)` / `registerShape(name,
  definition)`. The catalog uses this to register its own objects; the
  registry is public so custom objects register (or are used directly
  without registering) the same way.
- **Randomizer**: given an object definition, `randomize(definition, seed?)`
  picks a valid random combination of slot variants + a palette from the
  definition's allowed overrides. Deterministic when a seed is passed
  (needed for reproducible tests and for consumers who want repeatable
  "random" personas, e.g. seeded by user ID).

### Movement & interaction (`8bot/core`)

Because parts are placed by adding `slot.position` at compose time, moving a
limb is just composing again with a per-slot pixel offset — no rotation or
redrawing of pixel data required.

- **`SlotDefinition.role?: "limb" | "body" | "accessory"`** — marks which
  slots are limbs (legs, thrusters, arms) so generic tooling (like
  `walkCycle`) can find them without knowing an object's specific slot
  names or count. Un-marked slots default to non-limb.
- **`Pose`**: `Record<slotName, { dx?: number; dy?: number }>` — a pixel
  offset added on top of a slot's base `position` for one compose call.
  `compose(definition, choices?, paletteOverrides?, pose?)` gains a fourth,
  optional parameter.
- **`walkCycle(definition, t)`**: given any object definition and a time/
  frame value `t`, returns a `Pose` that alternates limb slots (even index
  vs. odd index) through a small vertical offset using `sin(t)`, producing
  a natural-looking walk for any limb count — 2, 4, or 8 legs, or thrusters
  on a flying bot — with no per-object animation code. The consumer drives
  `t` themselves (e.g. from `requestAnimationFrame` in a React
  `useEffect`), calls `compose(definition, choices, palette,
  walkCycle(definition, t))` each frame, and re-renders.
- **`getBounds(object, position?, pixelSize?)`**: returns `{ x, y, width,
  height }` for a Composed Object at a given world position, in the same
  units the renderer draws in (`pixelSize` scales it, matching the
  renderer's own `pixelSize` option). **`intersects(a, b)`**: plain AABB
  overlap check between two `Bounds`. Consumers use these two functions to
  compare an object's on-screen bounds against `element.getBoundingClientRect()`
  (or a game entity's bounds) and decide what "interacting" means in their
  own app — 8bot does not touch the DOM or track world position itself.

### 2. Catalog (`8bot/catalog`)

Built-in object definitions, each in its own folder under `catalog/`
following one convention: a folder with its part grids, slot definition,
default palette + allowed overrides, and an `index.ts` that calls
`registerObject`/`registerShape` and exports `createX(options)` +
`randomX(seed?)`. A top-level `catalog/index.ts` re-exports every object.
Adding a new object = adding a new folder that follows this convention +
one line in the top-level index — no core code changes required.

**v1 catalog (9 objects, 4 structural kinds):**

| Kind | Objects | Slots (example) |
|---|---|---|
| Character (humanoid) | Human | head, torso, arm×2, leg×2 |
| Character (quadruped) | Elephant | body, leg×4, trunk, ear×2 |
| Robot (variable-limb) | Octopod | body, leg×8 |
| Robot (variable-limb) | Tetrapod | body, leg×4 |
| Robot (variable-limb) | Flying bot | body, thruster×2/4, no legs |
| Robot (variable-limb) | Uni-eyed UFO | saucer body, eye (single, central), no limbs |
| Prop | Tree | trunk, foliage×1-3 |
| Primitive shape | Cube, Oblongoid, Sphere | n/a — extent + base color, auto-shaded |

Each character/robot exposes `createX({ parts?, palette? })` (explicit) and
`randomX(seed?)` (randomized). Each primitive exposes `createX({ size?,
color? })` and `randomX(seed?)`. Every character/robot definition marks its
leg/arm/thruster slots with `role: "limb"` so `walkCycle` works on all of
them out of the box (Human, Elephant, Octopod, Tetrapod, Flying bot). The
UFO has no limb slots and does not animate; Tree and the primitive shapes
have no slots at all.

### 3. Renderers (`8bot/canvas`, `8bot/svg`)

Thin adapter functions that take a Composed Object + render mode
(`"flat"` or `"isometric"`) and draw it:

- `8bot/canvas`: `drawToCanvas(ctx, composedObject, { mode })` — draws
  pixels as filled rects (scaled by a pixel-size option) onto a
  `CanvasRenderingContext2D`.
- `8bot/svg`: `toSvgString(composedObject, { mode })` /
  `renderToSvgElement(...)` — produces SVG markup (one `<rect>` per pixel
  or run-length-encoded rects for size) for DOM insertion or serialization.

Both are optional — the Composed Object shape (plain data: arrays of pixel
rects with color/position/layer) is documented so consumers can write their
own adapter (WebGL, a game engine's sprite system, etc.) without needing
either renderer.

### Custom objects ("build your own")

Because the builder primitives (`Part`, `Palette`, object/shape definition
shape, `registerObject`/`registerShape`, `composer`) are the actual public
API — not a wrapper around a hidden internal format — a consumer defines a
custom object (e.g. a palace prop) exactly the way catalog objects are
defined internally, then composes and renders it the same way. Catalog
source doubles as reference examples.

## Data flow

1. Consumer calls `catalog.human.randomHuman(seed)` (or
   `createHuman({ palette: {...} })`, or their own custom definition
   through `core.compose(definition, chosenParts, palette)`).
2. This returns a **Composed Object**: plain, renderer-agnostic pixel data.
3. Consumer passes it to `drawToCanvas` / `toSvgString`, or their own
   adapter, with a render mode.

## Error handling

- `compose()` throws a descriptive error if a required slot has no part
  assigned and no default exists, or if a palette override references a
  region tag not present in the definition.
- `randomize()` never throws for a valid, registered definition — it only
  selects among variants already declared valid by that definition.
- Renderers assume a well-formed Composed Object (produced only by
  `compose()`); they don't re-validate pixel data.

## Package & tooling

- Single npm package `8bot`, TypeScript source.
- Subpath exports: `8bot/core`, `8bot/catalog`, `8bot/canvas`, `8bot/svg`
  (root `8bot` re-exports core + catalog for convenience).
- Build: **tsup** → ESM + CJS + `.d.ts` per entry point.
- Tests: **Vitest** — composer output shape, palette application/override
  validation, randomizer determinism given a seed, one snapshot-style test
  per catalog object confirming it composes without error.
- Existing `package.json` fields (name, repo, license, author) are kept;
  the placeholder `test` script is replaced with `vitest run`.

## Testing strategy

- Unit tests in `core`: part/palette merge logic, slot validation, error
  cases, randomizer seeding, `walkCycle` output shape and alternation across
  varying limb counts, `getBounds`/`intersects` correctness.
- Unit tests per catalog object: composes successfully with defaults, with
  a random seed, and with a valid palette override; rejects an invalid
  region-tag override.
- Renderer tests: given a small fixed Composed Object, `toSvgString`
  produces expected markup; `drawToCanvas` calls the expected `fillRect`
  sequence (mocked context).
